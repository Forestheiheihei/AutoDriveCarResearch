# AutoDriveCarResearch

本仓库用于持续收集、整理指定车型的**智能驾驶/驾驶辅助功能负面反馈**，并将收录数量与车型销量作粗略对照。后续工作以“新增车型”或“为已有车型追加新记录”为主，不随意改变统计口径、字段结构和历史记录。

## 一、项目范围

### 1. 只收录智驾相关负面反馈

收录范围包括但不限于：

- 高速/城市 NOA、领航辅助、导航辅助驾驶异常；
- ACC、LCC、车道居中、车道保持、自动变道等功能异常；
- AEB、FCW 等主动安全功能在相关场景下未按预期工作，或出现误触发；
- 自动泊车、遥控泊车、记忆泊车异常；
- 智驾系统无法开启、频繁退出、功能不可用；
- 摄像头、激光雷达、毫米波雷达、域控制器等硬件/软件故障，且明确影响智驾功能；
- 误识别、漏识别、错误限速、异常制动/转向、路线决策不合理、接管提示异常等实际体验问题。

**不收录**与智驾无关的普通质量问题、车机娱乐问题、续航/充电问题、内饰异响、售后态度等。除非该问题直接导致智驾功能异常，否则不得因为同一投诉中夹带其他质量问题就将其计入。

### 2. 车型范围

当前车型以 `reasearch.csv` 第一行表头为准。新增车型时，在 CSV 和 XLSX 中同步增加一列，并统一车型名称。车型配置、动力版本、智驾硬件/软件方案不同的，应在记录正文中明确区分，不要将不同版本混为同一具体配置。

## 二、数据来源与搜索原则

搜索不能只看正式投诉帖或独立发帖。应尽量覆盖：

1. 车主论坛、车型论坛、汽车之家车友圈/口碑；
2. 车型介绍页、车型详情页、车主口碑页下方的评论区；
3. B站视频评论区、动态、车主实测内容的评论区；
4. 懂车帝、易车、知乎等平台的车主内容与评论；
5. 车质网、黑猫投诉等投诉平台；
6. 微博、小红书等社交平台；
7. 汽车媒体实测、长期测试和专业评测。

### 评论区重点规则

- **必须主动检查评论区**，尤其是车型介绍、车型对比、试驾、智驾功能介绍、车主提车/用车视频的评论区。
- 评论区可能包含直接发帖中没有出现的真实问题线索，应把有明确车型和智驾问题描述的评论作为候选记录。
- 部分负面独立帖可能因删除、隐藏或其他原因无法继续访问，因此不能只依赖搜索引擎能检索到的独立帖子。评论区线索同样需要记录来源页面、评论日期（可见时）和原始链接。
- 不得把评论区中没有具体事实支撑的情绪化评价、玩笑、猜测或转述，当作已核实的车主事件。
- 页面无法访问、评论已删除或内容不完整时，标记为“无法复核/待复核”，不得补写或推测缺失内容。

## 三、入库前去重规则（强制）

每条候选反馈在写入前，都必须与现有 CSV 和已收录来源进行重复检查。

### 1. 判定重复

出现以下情况时，原则上视为同一条反馈，不重复计数：

- 同一车主、同一事故/故障，被不同平台转载；
- 同一投诉在投诉平台更新、追加说明或再次发布；
- 同一视频/帖子被多个账号搬运，描述的是同一事件；
- 同一评论被截图转发或在不同文章下重复引用；
- 同一事件仅因标题、措辞或发布日期不同而看起来像多条记录。

### 2. 可以分别计数的情况

- 同一车主在不同日期、不同道路场景中明确描述了不同事件；
- 不同车主分别报告了独立发生的问题；
- 同一车型存在多个独立故障案例，且有足够信息区分。

### 3. 去重时的处理方式

- 优先保留信息最完整、最接近原始发布者、链接最稳定的来源。
- 其他转载链接可作为补充来源写入同一条记录，不另起一条。
- 无法确认是否重复时，先标记“疑似重复/待核验”，暂不计入正式数量。
- 不得为了增加负反馈数量而拆分同一事件，也不得为了减少数量而合并明显独立的事件。

## 四、记录质量与分类

每条记录尽可能包含：

- 反馈日期；
- 来源平台和原始链接；
- 车型、年款、具体配置；
- 智驾方案/供应商/硬件配置（能确认时填写）；
- 软件版本（能确认时填写）；
- 具体功能和发生场景；
- 用户描述的异常表现及后果；
- 证据状态与核验说明。

建议在记录文字中明确标注以下性质：

- **车主投诉**：投诉平台中可定位到具体车主和车型的记录；
- **车主反馈**：论坛、口碑、评论区等车主自述；
- **媒体实测**：媒体或测评人员亲自测试得到的问题；
- **评论区线索**：评论区中有具体场景但身份/细节尚不完整的内容；
- **待核验线索**：只有标题、搜索摘要或不完整页面，尚未读到完整内容。

以上类型不得混淆。车主单方陈述只代表“车主如此反馈”，不直接等于已证明系统存在缺陷或事故责任已经确定。

## 五、CSV 文件格式约定

主数据文件：`reasearch.csv`

采用 UTF-8 编码、逗号分隔的宽表结构：

- 第一列：`记录类型`
- 第二列：`记录日期/统计月份`
- 后续每一列：一个车型，车型名称写在第一行表头。
- 每条负反馈占一行，只在对应车型列填写内容，其余车型列留空。
- 销量基准记录单独占一行，不能混入负反馈记录。
- 不得擅自调整既有列的顺序、名称或字段含义。
- 新增车型时，必须同时更新 CSV 表头和 XLSX 对应车型列。
- 记录内容中的逗号、引号、换行必须按 CSV 标准正确转义；提交前检查每行列数必须完全一致。

建议负反馈单元格统一采用以下结构：

`来源类型｜反馈日期｜年款/配置｜智驾方案/版本（未知写“未知”）｜问题场景与表现｜核验状态｜原始链接`

若某字段未知，明确写“未知”或“未披露”，不要猜测。链接尽量指向原始帖子、原始评论所在页面或投诉详情页，而不是搜索结果页。

## 六、XLSX 统计表格式与计算口径

统计文件：`智驾负反馈与销量统计.xlsx`

保持用户约定的四行结构，每一列对应一个车型：

| 行 | 内容 | 规则 |
|---|---|---|
| 第1行 | 车型名称 | 与 CSV 表头车型名称一致 |
| 第2行 | 负反馈数量 | 该车型当前已入库、去重后的智驾负反馈记录数 |
| 第3行 | 销量 | 采用统一统计月份的车型销量，单位为辆 |
| 第4行 | 比值 | 负反馈数量 ÷ 销量 |

第四行使用 Excel 公式计算，不手工填写静态结果。销量缺失或无法核验时，销量与比值留空，不得用 0 代替未知销量。

### 计算解释

本项目按用户约定，使用：

`负反馈数量 ÷ 销量`

作为车型之间的**粗略对照指标**。必须同时注明负反馈数量的统计范围和销量月份。

该比值不是严格的车辆故障率、事故率或智驾失效率：负反馈是网络可见且被本项目收录的记录，存在发帖意愿、平台审核、内容删除、车型保有量、搜索覆盖程度等偏差；销量是某一统计月份的销量，也不等于同期实际使用车辆数。因此只能用于当前样本的横向观察，不能直接推断真实故障概率。

为保证车型之间可比较，销量应尽量使用同一来源、同一统计口径、同一月份的数据。若只能找到不同月份或不同口径的数据，必须在表内/备注中明确标注，不得伪装成可直接比较的数据。

## 七、每次新增记录后的必做事项

每次搜索到新反馈并准备入库时，必须依次完成：

1. 确认内容确实涉及智驾负面问题，不符合范围的剔除。
2. 打开原始页面，尽可能阅读正文和评论区；仅有搜索摘要的，标记待核验。
3. 检查 CSV 中是否已有相同投诉编号、相同链接、相同车主/事件或转载内容。
4. 判断是否为独立事件；疑似重复的先不计数。
5. 按统一格式追加到对应车型列，不改动无关记录。
6. 更新 XLSX：重新计算各车型去重后的负反馈数量，核对销量统计月份和来源，更新公式。
7. 检查 CSV 每行列数、XLSX 车型顺序、公式和空值处理。
8. 将 CSV 与 XLSX 一并提交到 GitHub `main` 分支。
9. 在提交说明或工作汇报中简要列出新增记录数、去重数、待核验数、销量数据变化和文件链接。

**重要：入库 CSV 后不能遗漏 XLSX 更新。** CSV 是明细数据主表，XLSX 是根据 CSV 和销量数据生成的统计表；两者必须保持一致。

## 八、维护守则

- 只追加经过范围判断和去重检查的新数据；不要无理由重写或清空历史记录。
- 不把“没有搜到”写成“没有负面反馈”。
- 不把投诉标题、评论区传言或媒体推测写成已证实事实。
- 不编造车主身份、车型配置、智驾供应商、软件版本、销量或链接。
- 来源失效时保留原始记录，并标记链接失效；如找到转载或缓存来源，可补充而不是覆盖原始信息。
- 发现错误时保留可追溯的修订说明，避免静默篡改统计口径。
- 所有车型使用相同的纳入、去重和计数标准。
- 每次提交前检查 GitHub 当前 `main` 分支最新文件，避免基于旧版本覆盖新数据。
